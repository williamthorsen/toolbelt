# Toolbelt

## Overview

PNPM monorepo of TypeScript utility libraries, each published to npm as `@williamthorsen/toolbelt.{domain}`. Every package organizes its source by API maturity and exposes each tier as a separate export subpath, so consumers opt in to the stability that they want. Node >= 24, ESM only.

## Project structure

- `packages/{domain}/`: one published library per domain (arrays, async, datetime, dstructs, enums, errors, filesystem, git, guards, hof, jira, numbers, objects, packaging, sets, statistics, strings, testing, tools, vitest).
- `packages/adoption/`: private shared layer for the packages' ReadyUp adoption kits, excluded from release processing in `.config/release-kit.config.ts`. It exports `./src/mod.ts` directly rather than a build, following `packages/tools`, and esbuild inlines it at `rdy compile`, so it never publishes and never resolves for a consumer. A second export, `./test-utils`, is a barrel reaching `createTrackedRepo` and the helpers that run a check and read its report from a package's own kit test, and is held out of `mod.ts` on purpose: every module reachable from `mod.ts` lands in each kit's manifest `inputs[]`, so putting a test helper there would add `node:child_process` to every bundle's input list. Its assembler applies readyup's `ownImplementation` exemption, so a package's own implementation of an idiom is not reported as a candidate to adopt it, while a neighbouring declaration in the same file is. It declares no workspace dependency: every kit-bearing package devDeps it, foundation packages included, so a dependency of its own closes a cycle (`errors` devDeps `adoption`, and `filesystem` deps `errors`), which is why its test scaffolding, `createTempDir` and `pointCwdAt`, is held to node builtins rather than taken from `filesystem` and `testing`. `__tests__/workspace-dependency-graph.app.unit.test.ts` is what fails on a reintroduced cycle. Holding no tier directories, it falls outside `__tests__/workspace-exports.app.unit.test.ts`.
- `packages/_template/`: private scaffold for new packages, excluded from release processing in `.config/release-kit.config.ts`.
- `packages/{domain}/src/{0-strawman,1-proposed,2-draft,3-candidate,4-release}/`: maturity tiers, each exported one holding an `index.ts` that re-exports its public surface. `src/bin/`, `src/internal/`, `src/readiness/`, `src/types/`, and `src/test-utils/` sit outside the tiers and are not exported. `internal/` and `types/` still ship, being build entry points, so `__tests__/support-module-usage.app.unit.test.ts` requires every module in one to have an importer outside test scaffolding; `test-utils/` the build drops, which is what keeps a test helper out of `dist/`. `bin/` ships as well, holding a package's executables, which reach a consumer through the `bin` field rather than through `exports`. An entry point that nothing imports is what `support-module-usage` reports, so `bin/` is outside its scope, and `__tests__/bin-target-resolution.app.unit.test.ts` holds each declared target to a source module carrying a shebang instead. A dependency imported only by a bin would fail `dependency-reachability`, whose walk starts at the exported tier indexes, so a CLI is written against node builtins and the package's own tiers. `readiness/` backs a package's ReadyUp kit, which `rdy compile` bundles on its own, and a package holding one drops it from the build through `build.extraIgnorePatterns` in its own `.config/nmr.config.ts`. It holds the package's detector and the export list against which adoption is counted, and nothing else: the scanning primitives, the path judgments, the site hand-off rules deciding which kit claims an idiom recognized by two of them, and the kit assembler live in `packages/adoption`, and the sweep, the adoption count, and the finding report come from `readyup/check-utils`.
- `.agents/`: `codeassembly.yaml` declares the guidance packages resolved by `codeassembly sync`; `preferences.yaml` carries the project slug and ticket-ref prefix.
- `.config/`: tool configs. Vitest config lives outside it, in exactly two root files: `vitest.config.ts` and `vitest.root.config.ts`, each a bare call to a `@williamthorsen/nmr/vitest` factory.
- `test-utils/`: the root test suite's shared helpers, covered by their own `__tests__/`. Nothing here imports a workspace package: the root manifest declares no workspace dependency, and that is what keeps `nmr root:test` green on a tree where no package has been built. `nmr ci` builds before it checks, so a workspace import added here passes CI and fails only on a fresh clone.

Versions are independent per package.

## Commands

Runner conventions (discovery, invocation, root vs. package registries, hooks) come from the ambient `nmr` rulebook, which `codeassembly sync` writes into the machine-local guidance files. CI runs `pnpm exec nmr ci` (`.github/workflows/code-quality.yaml`); a dependency audit runs separately, on pull requests and daily (`.github/workflows/audit.yaml`). `pnpm exec rdy run --packages` runs the adoption checks shipped by its configured packages, this repo's own kits included: readyup resolves a configured package through the workspaces where `node_modules` misses, so the root manifest declares no dependency on the toolbelt workspaces. What it reports against this repo's sources is an adoption decision left open, not a defect. Nothing in CI runs it, so run it by hand after a dependency upgrade.

## Architecture

**Build.** There is no repo-local build script: `nmr build` delegates to the managed `nmr-compile`. Typechecking is separate, via `tsgo` (`@typescript/native-preview`), independent of the `typescript` package.

**Compiler options.** Root `tsconfig.json` extends `@williamthorsen/tsconfig` (`@tsconfig/strictest` inlined, plus a Node-only layer at ES2025). Packages extend the root and declare no `compilerOptions`, carrying only `$schema`, `extends`, and `include`.

**Exports.** `package.json` maps each maturity tier to its own subpath:

- default: `4-release`
- `/candidate`: `3-candidate`
- `/draft`: `2-draft`
- `/proposed`: `1-proposed`

`0-strawman` is unexported, and a package holding one drops it from the build through `build.extraIgnorePatterns` in its own `.config/nmr.config.ts`, so it does not ship either. `__tests__/workspace-exports.app.unit.test.ts` enforces the correspondence in both directions: every export target names a tier holding an `index.ts`, and every tier but `0-strawman` has a subpath. A workspace with no tier directories, such as `tools`, is out of its scope.

Three audits hold that shape, all walking source so they pass on an unbuilt tree. `__tests__/strawman-exclusion.app.unit.test.ts` fails on a package holding `src/0-strawman/` whose own config does not declare the pattern, and on any module outside a strawman importing into one, which is what `extraIgnorePatterns` alone does not prevent: it drops a directory as an entry point rather than from the emit. `__tests__/tier-module-reachability.app.unit.test.ts` fails on a module in an exported tier that no tier index reaches, and `__tests__/dependency-reachability.app.unit.test.ts` fails on a `dependencies` entry imported by no exported module, skipping a private workspace, which installs for nobody. Reachability spans a package's exported tiers together, so a module imported by a neighbouring tier is published through that tier's index.

**The dependency set is the package's, not the subpath's.** npm scopes `dependencies` to the package while the tiers are subpaths of it, so a consumer importing the release entry point installs what every tier needs. This is accepted rather than worked around: a consumer taking `pluralize` from `toolbelt.strings` additionally installs `arrays`, `numbers`, `sets`, and `guards`, which is 22.2 kB of JavaScript, all first-party and none of it carrying an external dependency of its own. Three mechanisms were weighed and rejected. Splitting each domain into a release package and a preview package is the only one that makes every dependency reachable from the entry declaring it, and it presupposes populated release tiers, which most packages do not have; optional peers are not resolved transitively, so a `/candidate` consumer would hand-install the closure; `optionalDependencies` install by default and so save nothing. Reopen the decision when a release tier holds enough API that the default entry is what third parties import.

**Cross-package imports** use the published name plus the maturity subpath (`import { SeededRng } from '@williamthorsen/toolbelt.numbers/candidate'`), never relative paths across a package boundary. Workspace deps are declared `workspace:*`.

**Scaffolding.** A new package is scaffolded under its own ticket. The outcome is an empty package identical to `packages/_template` but for names, descriptions, and metadata fields, with `version` in `package.json` set to `0.1.0`. The API that it will hold, and any migration of existing packages onto it, belong to later tickets. Three files record the new package: an entry in `.config/release-kit.config.ts`, the `.github/labels.yaml` regenerated from it by `release-kit sync-labels generate`, and a label lookup added by hand to `.meta/label-map.json`.

**Adoption.** A utility earns a place by cross-repo demand, or by supplying a capability that its platform structurally lacks -- the language for most packages, Vitest for `vitest`. Hand-roll count alone is not the measure: a helper hand-rolled by nobody may only show that people settle for the platform's weaker alternative. Adopting one from another repository reconsiders its API; it is not a port.

**Test-utility routing.** A test-only utility goes to `vitest` if it is Vitest-specific, whether by importing the runner's API or by producing a value shaped for it, and to `testing` if it is runner-agnostic. `makeFixture` is the second kind of Vitest-specific: it imports nothing and is worthless without the runner. Every other utility goes to its domain package. A helper for the root suite itself is the exception and stays in root `test-utils/`, since importing one from a workspace would need a built tree. `__tests__/runner-agnostic-imports.app.unit.test.ts` enforces the split, exempting a workspace that declares Vitest under `dependencies` or `peerDependencies` -- the fields that install it for a consumer. It tests the import half alone, so a runner-shaped utility that imports nothing passes it either way.

**Release.** Run release-kit locally (`prepare`, `commit`, `tag`), then `git push && git push --tags`. The tag push triggers `publish.yaml`, which publishes with provenance via npm trusted publishing (OIDC); the repo holds no `NPM_TOKEN`. Tags must be pushed from a developer machine: GitHub does not fire workflows for tags pushed with `GITHUB_TOKEN`, so the dispatch `release.yaml` path alone cannot publish.

## Code style

- Intra-package imports carry an explicit `.ts` extension (`./shuffle.ts`). `allowImportingTsExtensions` is on and `nmr-compile` rewrites it at build time.
- Exported functions in a maturity tier carry JSDoc `@category` and `@stage {maturity}`, plus `@experimental` where applicable. Keep `@stage` in sync with the containing folder; `__tests__/stage-tag-alignment.app.unit.test.ts` enforces this.
- Exported functions in `src/bin/`, `src/internal/`, and `src/readiness/` carry `@internal` instead. None is a maturity tier, so none has an `@stage` value to take, and the alignment test derives a tier only from a `src/{n}-{tier}/` segment -- any `@stage` there is unvalidated by construction.
- Tests live in `__tests__/` beside the source, named `{subject}.{tier}.test.ts`. `describe()` takes the function reference, not a string: `describe(shuffle, () => ...)`.
- `expectTypeOf` is imported from `vitest`, which re-exports it bare. `expect-type` is deliberately undeclared, so a direct import does not resolve.
- Dependency versions are pinned exactly (`savePrefix: ''` in `pnpm-workspace.yaml`). A specifier used in more than one manifest moves to that file's `catalog:` block, and every site reads `catalog:`.
- External runtime dependencies are avoided rather than forbidden: reach for one only where hand-rolling would be worse, and prefer a workspace helper where one fits.
- Name a function by what it returns and what it does: `find*` for one result or none, `list*` for an array, otherwise the most specific accurate verb, with any other container named in the tail (`extractPlaceholderSet`). `get*` is the fallback for when no more specific verb is accurate, not the default.
- Scope-bound utilities are `using` + `Disposable`; one-shot helpers are plain functions. A `Disposable` composes upward into a hook-registering wrapper and the reverse does not, so it is the form to reach for where both would serve.

## Gotchas

- **`4-release` is empty for most packages.** Most hold `export {}` there, with the real API in `3-candidate`. Import from `/candidate` unless you have confirmed the symbol is promoted.
- **Promoting an API is a move plus three edits**: relocate the file, update both tiers' `index.ts`, and update the `@stage` tag.
- **Suites are Vitest projects selected by filename, not by config file.** The projects are the isolation ladder `unit`, `tool`, `localhost`, and `remote`, named for the furthest thing that a test reaches and matched on the segment immediately before `.test.ts`. `unit` is the residual: any other segment lands there, which is why `stage-tag-alignment.app.unit.test.ts` carries its tier in the tail and leaves `app` as documentation. `nmr test` runs `unit` and `tool`; `nmr test:all` runs everything.
- **`passWithNoTests` is set on every project.** A suite with no matching files exits green instead of failing, so a package that loses its tests passes just as quietly. The placeholder `todo` test in `packages/_template` is what keeps a freshly scaffolded package from being the first such case.
- **Packages carry no Vitest config.** Vitest walks up from the run directory to the root `vitest.config.ts` while keeping `root` at the cwd, so `nmr test` inside a package collects that package's tests alone. A per-package config re-adds a file that changes nothing.
- **`strict-lint` downgrades some rules to warnings.** The set is `advisoryRuleSeverities`, exported by `@williamthorsen/eslint-config-typescript`; violations of those rules do not fail `check:strict`. The repo holds no local deferral list of its own.
- **pnpm enforces a release soak before newly published third-party versions install.** See `minimumReleaseAge` in `pnpm-workspace.yaml` for the window and the first-party exclusions.
- **A committed kit bundle goes stale silently, and `packages/adoption` makes it stale in two places at once.** `rdy compile` writes `.readyup/kits/default.js` and the hashes in `.readyup/manifest.json`; editing a kit source, a `src/readiness/` module, or anything under `packages/adoption` leaves both behind until you recompile in each kit-bearing package. `__tests__/kit-bundle-freshness.tool.test.ts` is what fails on it, and a formatter run over a kit source is enough to trip it.
- **`makeFixture` depends on its own emitted source.** Vitest discovers a fixture's dependencies by parsing the fixture function's parameter list, and it reads the shipped code, so the empty destructuring pattern in `toolbelt.vitest`'s `makeFixture` is load-bearing output rather than a stylistic choice. The build is `tsc` at `ES2025` with no minifier, which preserves it; adding a minifier or lowering the target would break every consumer while the source-run test suite stayed green.
